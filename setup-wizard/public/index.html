Study setup

1 · Choose your backend

The study needs a Supabase backend (a free Postgres database in the cloud, or one running on your own machine). It only ever stores encrypted data:

Pick one:

  1. Go to supabase.com, create an account and a New project (choose any name and a strong database password; pick a region near your participants).
  2. When it finishes provisioning: Settings → API — copy the Project URL and the anon / publishable key below.
  3. Connect (top bar) → Session pooler — copy the connection string (starts with postgresql://) and put your database password into it.

Enter the same three values used when the backend was first set up. Step 2 will only verify the backend (no reinstallation), and in step 3 your new study is simply added next to the existing ones.

  1. Install the Supabase CLI and Docker, then run supabase start in a terminal.
  2. URL: http://127.0.0.1:54321 · anon key: printed by supabase status.
  3. Connection string: postgresql://postgres:postgres@127.0.0.1:54322/postgres

2 · Provision the backend

This backend was set up before — no database installation is needed. Verify it below, then just load the keys (b) and write this app's credentials (c).

a) Database setup

Creates the tables, security policies and functions the app needs. Safe to re-run at any time.

The database is already in place. Verify it — and re-run the setup only if something is reported missing (for example after updating this toolkit); it never touches existing data.

    b) Study keys

    Two keypairs: the PI key (decrypts study data on your machine — private key never leaves it) and the receipt key (signs deletion receipts). Stored in a folder that is never committed to git — back it up offline.

    c) App credentials

    Writes the URL and anon key from step 1 into local.properties, where the app build reads them (they never go into source code).

    d) Withdrawal function in the Supabase dashboard

    Already deployed during the first setup — just confirm it still responds. The steps reappear if the check fails.

    The signed-deletion function runs on Supabase's servers. Deploy it once from the dashboard — no extra tools needed:

    1. Dashboard → Edge Functions (left sidebar) → Deploy a new function → Via Editor.
    2. Name it exactly confirm-withdrawal, replace the sample code with the real one , then press Deploy.
    3. Leave Verify JWT ON (the default). Only a participant's own signed-in session may withdraw; the function also checks the device signature. If you turned it off for an earlier version, switch it back on.
    4. Authentication → Providers → Email: keep it enabled and switch Confirm email → OFF. Participant accounts use generated addresses (…@participants.invalid) that never receive mail; with confirmation on, enrolment cannot sign in.
    5. Edge Functions → Secrets → add a secret (enables the signed "proof of deletion" receipts):
      Name: DELETION_SIGNING_KEY_PKCS8_B64
      Value: 
      ← generate the keys in box b first
    Prefer the CLI? 
    supabase link --project-ref <your-project-ref>
supabase secrets set DELETION_SIGNING_KEY_PKCS8_B64=<generate keys first>
supabase functions deploy confirm-withdrawal

    3 · Define your study

    This is what participants see and consent to. For each data type, pick the measurement schemas that feed it — that choice also wires the app.

    Loads a study from the backend into the form below. The update is re-signed and keeps the study's id, so enrolled participants stay enrolled; their app asks them to consent again to any new or changed data type before it is collected.

    Investigator handover. This wizard's PI key (backend/keys) is not the study's PI key. To hand the study to a new investigator, prove control of the current one by selecting the current PI's private key (pi_private.pem). It is only used to sign a challenge here and is never stored or uploaded. After the update, new data is encrypted for the new PI key; data collected before stays readable only with the old key.

      Enrolment and end of study. These take effect at once — no new version or re-consent. Closing enrolment stops new participants from joining; everyone enrolled keeps taking part. Ending the study is permanent: the backend refuses new enrolments, consent and data measured after the end; participants' apps stop collecting, upload what was recorded before, and tell them the study has ended. Their data stays until its retention period ends, or until they withdraw.

      Questionnaires (optional)
      
      
      Questions participants answer in the app. The app draws the form from what you publish here,
         so a new version reaches every phone without an app update — signed with your study-signing
         key, so nobody else can change the questions.
      
      
      Each questionnaire belongs to one data type of the study, and that is what participants
         consent to: its name, description, retention and — through Sampling — how often
         (e.g. 72000 s ≈ once a day). Publishing a new version of the questions therefore does
         not ask participants to consent again. Keep the questions within what the data type
         describes and check with your ethics committee whether a change needs approval; a change that
         needs new consent is a change to the data type (update the study).
